# OpenWrt 25.12.6 — оптимизированная сборка для Xiaomi AX3200 / Redmi AX6S

[![Скачать последний релиз](https://img.shields.io/github/v/release/Dreyk007/openwrt-ax3200?style=for-the-badge&label=%D0%A1%D0%BA%D0%B0%D1%87%D0%B0%D1%82%D1%8C&color=2ea44f)](https://github.com/Dreyk007/openwrt-ax3200/releases/latest) [![Установка](https://img.shields.io/badge/%D0%A3%D1%81%D1%82%D0%B0%D0%BD%D0%BE%D0%B2%D0%BA%D0%B0-0969da?style=for-the-badge)](#установка)

**Какой файл скачать:**
* **первая установка** со стоковой прошивки — файл, имя которого заканчивается на `factory.bin`;
* **обновление** с OpenWrt 24.10 / 25.12 — файл, имя которого заканчивается на `squashfs-sysupgrade.itb`.

Остальные случаи (OpenWrt 23.05 и старше, возврат на стоковую прошивку) описаны в разделе [«Установка»](#установка).

Этот репозиторий (ветка **`xq-25.12`**) — форк стабильного релиза **OpenWrt 25.12.6** (`Linux 6.12.112`), адаптированный для **Xiaomi Router AX3200 (RB01) / Redmi Router AX6S (RB03)** на платформе **MediaTek MT7622B + MT7531BE + MT7915E** (включает доработки MediaTek из дерева `remittor`).

Цель сборки — **гигабит по кабелю и Wi-Fi 6 на полной скорости, низкие задержки, защита NVRAM загрузчика от «окирпичивания» и полный набор функций домашнего роутера «из коробки»** при сохранении совместимости с официальным репозиторием пакетов OpenWrt.

> [!WARNING]
> Wi-Fi **включается при первом старте с общеизвестным паролем `12345678`**, а у веб-интерфейса **нет пароля root**. Задайте оба сразу после прошивки (LuCI → *Система → Администрирование* и *Сеть → Беспроводная сеть*).

## Коротко о главном
* **Маршрутизация на скорости линии почти без нагрузки на CPU:** аппаратный NAT (PPE) и ускорение Wi-Fi (WED) включены по умолчанию, а исправления ядра сохраняют при них правильную статистику трафика по клиентам и графики интерфейсов ([раздел 2](#2-аппаратное-ускорение-маршрутизации-и-wi-fi-6-hfo--wed)). Для медленных каналов с bufferbloat предустановлен SQM (CAKE) ([SQM или аппаратное ускорение?](#sqm-или-аппаратное-ускорение)).
* **Проверено на PC VR-стриминге:** проводной ПК передаёт клиенту 2×2 HE160 1,25–1,35 Гбит/с, а поток 200 Мбит/с, как у VR, идёт с пингом 1,7 мс (медиана) ([Wi-Fi 160 МГц и VR](#wi-fi-160-мгц-he160-и-vr-стриминг)).
* **Режимы работы в LuCI:** одна страница, *Система → Режим работы*, переключает наборы настроек, проверенные на этом роутере: сбалансированный (по умолчанию), максимум скорости провод → Wi-Fi с `bridger`, низкая задержка для VR и игр по Wi-Fi и SQM для медленных каналов ([Режимы работы](#режимы-работы)).
* **Более стабильный Wi-Fi:** 18 исправлений драйвера из ветки разработки mt76 (падения ядра при подключении клиентов и восстановлении прошивки радиомодуля, адаптивная чувствительность на 2,4 ГГц), настройки обоих диапазонов, подобранные под этот роутер, и 160 МГц на 5 ГГц по желанию ([раздел 4](#4-настройки-wi-fi-по-умолчанию-77_wireless), [HE160](#wi-fi-160-мгц-he160-и-vr-стриминг)).
* **Нет софт-брика «6 перезагрузок → оранжевый индикатор»:** флаги загрузки U-Boot проверяются при каждом старте ([раздел 3](#3-защита-nvram-от-софт-брика-6-перезагрузок--оранжевый-индикатор)).
* **Работают официальные пакеты:** ядро собрано так же, как официальное, поэтому пакеты `kmod-*` из официального репозитория устанавливаются и загружаются ([раздел 7](#7-совместимость-с-официальным-репозиторием-vermagic--apk)).
* **Оптимизация под Cortex-A53:** GCC 15, `-O2` с инструкциями ARMv8 Crypto и CRC32, LTO, регулятор частоты `schedutil` ([раздел 1](#1-компилятор-и-процессор-arm-cortex-a53)).
* **Обновления из веб-интерфейса:** роутер сам проверяет, не вышла ли новая версия сборки, показывает уведомление на странице «Обзор» и устанавливает обновление одной кнопкой ([Обновления прошивки](#обновления-прошивки)).
* **Всё готово к работе:** LuCI на русском и английском с темой Footstrap, шифрованный DNS (DoH), SQM, UPnP, DDNS, Wake-on-LAN, учёт трафика по клиентам, графики статистики и терминал в браузере ([Предустановленные пакеты](#предустановленные-пакеты)).
* **Ваши настройки переживают обновления:** настройки сборки применяются один раз для конфигурации, а не при каждой прошивке ([раздел 6](#6-как-применяются-настройки-99-custom-settings)).
* **Проверяемые релизы:** их собирает GitHub Actions из этого репозитория, и для каждого файла подписано подтверждение происхождения сборки ([Сборка и релиз через GitHub Actions](BUILDING.ru.md#сборка-и-релиз-через-github-actions)).

## Установка

> [!IMPORTANT]
> Сначала прочитайте [страницу Xiaomi AX3200 / Redmi AX6S в вики OpenWrt](https://openwrt.org/toh/xiaomi/ax3200). Там описаны **резервное копирование разделов флеш-памяти**, **восстановление по TFTP и через UART** и проблемы отдельных ревизий железа, которые здесь не повторяются. Прошивка сторонней микропрограммы — на ваш страх и риск.

**Известные риски (по данным вики):**
* У части новых экземпляров разделы MTD сдвинуты на `-0x20000`, и sysupgrade может их «окирпичить»; на некоторых не срабатывает даже factory-образ. Сообщается, что затронуты AX3200, выпущенные **после 12/2023** с отключённым telnet. Перед первым sysupgrade роутера, установленного из `factory.bin`, выполните проверки из вики («Known Issue #1»): вывод `hexdump /dev/mtd8 | head` должен начинаться с `0000000 0dd0 edfe`, а `fw_printenv | grep -e ^flag_try -e ^boot_fw` должен показывать `boot_fw1=run boot_rd_img;bootm`.
* Софт-брик «6 перезагрузок → оранжевый индикатор» предотвращается `bootcount` этой сборки, как только OpenWrt загрузилась (см. [раздел 3](#3-защита-nvram-от-софт-брика-6-перезагрузок--оранжевый-индикатор)).

**Резервный способ:** вернуться на стоковую прошивку и установить эту сборку уже с неё можно из любого состояния, даже если OpenWrt не загружается; см. [раздел Е](#е-возврат-на-стоковую-прошивку-и-xmir-patcher-резервный-способ).

### Файлы прошивки
Скачайте образы из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest) (при локальной сборке они появляются в `bin/targets/mediatek/mt7622/`):
| Файл | Назначение |
|---|---|
| `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin` | Первая установка со стоковой прошивки (или с OpenWrt ≤ 23.05). Содержит `ubi-loader`, дополненный до 512 КБ, и следом UBI-образ. |
| `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb` | Штатное обновление с OpenWrt 24.10 / 25.12 (разметка UBI). |
| `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-sysupgrade.ubi` | «Сырой» UBI-образ, извлечённый `build.sh` из `factory.bin`, для старых сборок, не принимающих `.itb` (см. ниже). |
| `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-ubi-loader.itb` | Отдельно загрузчик второго уровня (`ubi-loader`). |
| `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-initramfs-recovery.itb` | Initramfs-образ для восстановления (TFTP). |

**Как доставить образ на роутер.** В разделах Б–Д образ попадает в `/tmp` на роутере одним из двух способов:
* **Скачать прямо на роутере**, если у него есть доступ в интернет: ссылки `https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/<файл>` всегда ведут на последний релиз, а `sha256sums` оттуда же проверяет скачанный файл. Команды приведены в каждом разделе.
* **Скопировать с компьютера:** скачайте файл из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest) и скопируйте его командой `scp`; она есть в Linux, macOS и Windows 10/11 (в Windows можно также использовать WinSCP с протоколом SCP). Ключ `-O` нужен, потому что в OpenWrt нет SFTP-сервера.

Команды на роутере выполняются по SSH: `ssh root@192.168.1.1` (есть в Linux, macOS и Windows 10/11) или [PuTTY](https://www.chiark.greenend.org.uk/~sgtatham/putty/) в Windows — хост `192.168.1.1`, пользователь `root`. Пароль — тот, что задан для root в LuCI; сразу после прошивки его нет. Если адрес роутера не `192.168.1.1`, подставьте свой.

### А. Со стоковой прошивки через XMiR-Patcher (рекомендуется)
[XMiR-Patcher](https://github.com/openwrt-xiaomi/xmir-patcher) получает доступ по SSH через уязвимость стокового веб-интерфейса и сам прошивает образ. Работает в Windows, Linux и macOS.

1. Завершите первоначальную настройку стоковой прошивки (понадобится пароль веб-интерфейса) и подключите компьютер к **LAN**-порту роутера. Стоковая прошивка доступна по адресу `192.168.31.1`.
2. Скачайте XMiR-Patcher (*Code → Download ZIP*) и распакуйте.
3. Запустите: **Windows** — `run.bat`; **Linux/macOS** — установите Python 3.8+ и `openssl`, затем `./run.sh`.
4. Если адрес роутера не `192.168.31.1`, выберите `1 - Set IP-address`.
5. Выберите **`2 - Connect to device (install exploit)`** и по запросу введите пароль веб-интерфейса.
6. Выберите **`4 - Create full backup`**. Дампы всех разделов флеш-памяти сохраняются в папку `backups/` XMiR-Patcher — **сохраните их в надёжном месте**: в них уникальные для вашего экземпляра калибровочные данные, они нужны для возврата на сток и восстановления после брика.
7. Скачайте `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin` из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest) и скопируйте **только** этот файл в папку `firmware/` XMiR-Patcher (других образов там быть не должно).
8. Выберите **`7 - Install firmware (from directory "firmware")`** и дождитесь перезагрузки роутера.
9. Откройте `http://192.168.1.1` (пользователь `root`, без пароля), задайте пароль root и смените пароль Wi-Fi.

Если эксплойт не срабатывает на вашей версии стоковой прошивки, альтернативы (стоковая прошивка с telnet, методы `netmode 4`, UART) описаны в вики.

### Б. Обновление с OpenWrt 24.10 / 25.12
Настройки сохраняются. Начиная с r10 роутер умеет делать это сам: *Система → Обновления сборки AX3200 / AX6S* ([Обновления прошивки](#обновления-прошивки)).

1. Скачайте `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb` из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest).
2. В LuCI откройте *Система → Восстановление / Обновление*, в разделе *Установить новый образ прошивки* нажмите *Загрузка образа...*, выберите файл и нажмите *Загрузить*.
3. Оставьте отмеченным *Сохранить настройки и оставить текущую конфигурацию* и нажмите *Продолжить*. Роутер запишет образ и перезагрузится, это занимает несколько минут; не выключайте его в это время.

По SSH вместо этого: зайдите на роутер командой `ssh root@192.168.1.1`, скачайте и проверьте образ (последняя команда должна вывести `OK`), затем прошейте его:
```sh
cd /tmp
F=openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb
wget -O $F https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/$F
wget -qO- https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/sha256sums | grep -- $F | sha256sum -c -
```
```sh
sysupgrade /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb
```

### В. Обновление с OpenWrt 23.05 и старше (старая разметка)
Начиная с 24.10 у этого роутера другая разметка флеш-памяти: загрузчик второго уровня (`ubi-loader`), а за ним один раздел UBI с системой. `sysupgrade` из OpenWrt 23.05 и старше перейти на неё не может, поэтому образ один раз записывается вручную через `mtd`. **Все настройки сбрасываются.** Ниже — шаги способа 1 из [вики OpenWrt](https://openwrt.org/toh/xiaomi/ax3200#upgrading_from_2305_and_earlier_to_upcoming_2410_or_snapshot) (раздел *Upgrading from 23.05 and earlier to upcoming 24.10 or snapshot*, англ.); там же описан способ через TFTP. Другой путь — вернуться на сток, а затем XMiR-Patcher ([раздел Е](#е-возврат-на-стоковую-прошивку-и-xmir-patcher-резервный-способ)).

1. Сделайте резервную копию настроек: LuCI → *Система → Восстановление / Обновление* → *Создать архив*.
2. Поместите образ в `/tmp` на роутере. Если у роутера есть доступ в интернет, зайдите на него командой `ssh root@192.168.1.1` и скачайте образ прямо там (последняя команда должна вывести `OK`):
   ```sh
   cd /tmp
   F=openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin
   wget -O $F https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/$F
   wget -qO- https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/sha256sums | grep -- $F | sha256sum -c -
   ```
   Или скачайте файл из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest), подключите компьютер кабелем к LAN-порту и скопируйте файл:
   ```sh
   scp -O openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin root@192.168.1.1:/tmp/
   ```
3. Зайдите на роутер командой `ssh root@192.168.1.1` (если ещё не зашли) и выполните:
   ```sh
   mount -o remount,ro /
   mount -o remount,ro /overlay
   cd /tmp
   F=openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin
   dd if=$F bs=1M count=4 | mtd write - kernel
   dd if=$F bs=1M skip=4 | mtd -r write - ubi
   ```
   Если первая команда ответит `Resource busy`, не обращайте внимания. После последней команды роутер перезагрузится.
4. Откройте `http://192.168.1.1` (пользователь `root`, без пароля). Задайте пароль root и пароль Wi-Fi или восстановите архив из шага 1: *Система → Восстановление / Обновление* → *Загрузить архив...*.
5. Если вы восстановили архив, выполните по SSH, иначе следующие обновления (раздел Б) будут отклоняться:
   ```sh
   uci set system.@system[0].compat_version="2.0"
   uci commit system
   ```
   Восстановленные настройки заменяют настройки этой сборки (HFO, packet steering и другие); чтобы применить их поверх, см. [раздел 6](#6-как-применяются-настройки-99-custom-settings).

### Г. Старые сборки, не принимающие образ `.itb`
Некоторые старые сторонние сборки 24.10 (уже с новой разметкой) отклоняют `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb` с ошибкой `Cannot find ubinized rootfs in the factory FIT-image`. Тогда прошейте «сырой» UBI-образ. **Настройки не сохраняются.**

1. Сделайте резервную копию настроек: LuCI → *Система → Восстановление / Обновление* → *Создать архив*.
2. Поместите образ в `/tmp` на роутере. Если у роутера есть доступ в интернет, зайдите на него командой `ssh root@192.168.1.1` и скачайте образ прямо там (последняя команда должна вывести `OK`):
   ```sh
   cd /tmp
   F=openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-sysupgrade.ubi
   wget -O $F https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/$F
   wget -qO- https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/sha256sums | grep -- $F | sha256sum -c -
   ```
   Или скачайте файл из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest) и скопируйте его:
   ```sh
   scp -O openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-sysupgrade.ubi root@192.168.1.1:/tmp/
   ```
3. Зайдите на роутер командой `ssh root@192.168.1.1` (если ещё не зашли) и выполните:
   ```sh
   sysupgrade -n /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-sysupgrade.ubi
   ```
4. После перезагрузки откройте `http://192.168.1.1` (пользователь `root`, без пароля) и задайте пароли или восстановите архив из шага 1 (*Загрузить архив...*).

### Д. Обновление `ubi-loader` (при необходимости)
`sysupgrade` не трогает раздел `ubi-loader`: на роутере остаётся версия, записанная вместе с `factory.bin`. Чтобы обновить его до версии из этой сборки:

1. Поместите образ в `/tmp` на роутере. Если у роутера есть доступ в интернет, зайдите на него командой `ssh root@192.168.1.1` и скачайте образ прямо там (последняя команда должна вывести `OK`):
   ```sh
   cd /tmp
   F=openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-ubi-loader.itb
   wget -O $F https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/$F
   wget -qO- https://github.com/Dreyk007/openwrt-ax3200/releases/latest/download/sha256sums | grep -- $F | sha256sum -c -
   ```
   Или скачайте файл из [последнего релиза](https://github.com/Dreyk007/openwrt-ax3200/releases/latest) и скопируйте его:
   ```sh
   scp -O openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-ubi-loader.itb root@192.168.1.1:/tmp/
   ```
2. Зайдите на роутер командой `ssh root@192.168.1.1` (если ещё не зашли) и выполните (не выключайте роутер во время записи):
   ```sh
   mtd write /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-ubi-loader.itb ubi-loader
   reboot
   ```

### Е. Возврат на стоковую прошивку и XMiR-Patcher (резервный способ)
У стокового загрузчика есть режим восстановления: он устанавливает стоковую прошивку с компьютера по сети (TFTP). Он работает из любого состояния, даже если OpenWrt уже не загружается, — лишь бы был цел сам загрузчик. Часто это и самый простой путь со старой или сторонней сборки на эту: вернуться на сток, а затем [раздел А](#а-со-стоковой-прошивки-через-xmir-patcher-рекомендуется). **Все настройки сбрасываются**; если роутер ещё работает, сначала сделайте резервную копию (LuCI → *Система → Восстановление / Обновление* → *Создать архив*).

1. Скачайте стоковую прошивку своей модели (прошивку другой модели роутер не примет):
   * **Xiaomi AX3200 (RB01):** [`miwifi_rb01_firmware_bbc77_1.0.71_INT.bin`](http://cdn.awsde0-fusion.fds.api.mi-img.com/xiaoqiang/rom/rb01/miwifi_rb01_firmware_bbc77_1.0.71_INT.bin) с сервера Xiaomi;
   * **Redmi AX6S (RB03):** со [страницы загрузок Xiaomi](http://www1.miwifi.com/miwifi_download.html) или версию 1.2.7, которую советует вики OpenWrt ([зеркало](https://github.com/AoThen/AX6S-unlock/raw/master/miwifi_rb03_firmware_stable_1.2.7.bin)).
2. Подключите компьютер кабелем к LAN-порту роутера и запустите на нём DHCP- и TFTP-сервер:
   * **Windows:** официальная утилита Xiaomi [MiWiFi Repair Tool](http://bigota.miwifi.com/xiaoqiang/tools/MIWIFIRepairTool.x86.zip) сделает это сама: выберите файл прошивки и сетевую карту, к которой подключён роутер.
   * **Вручную** (Linux или [Tftpd64](https://pjo2.github.io/tftpd64/) в Windows с теми же настройками): задайте компьютеру статический адрес `192.168.31.100` с маской `255.255.255.0`, переименуйте прошивку в `C0A81F02.img` и раздавайте её папку, выдавая по DHCP единственный адрес `192.168.31.2` (роутер запрашивает файл, названный по своему адресу в шестнадцатеричном виде):
     ```sh
     sudo dnsmasq -i <interface> -p 0 -d -z --enable-tftp --tftp-root <folder> --tftp-no-fail --dhcp-range 192.168.31.2,192.168.31.2,255.255.255.0,12h
     ```
3. Отключите питание роутера, зажмите кнопку reset и включите питание. Когда оранжевый индикатор начнёт часто мигать (примерно через 10 секунд), отпустите кнопку: роутер скачает прошивку и установит её.
4. Когда индикатор часто замигает синим, стоковая прошивка установлена: отключите и снова включите питание. Мигание фиолетовым означает, что прошивка отклонена (не тот файл или прошивка другой модели); начните снова с шага 3.
5. Установите эту сборку, как описано в [разделе А](#а-со-стоковой-прошивки-через-xmir-patcher-рекомендуется), начиная с первоначальной настройки стоковой прошивки.

## Основные изменения

Файлы каждого изменения перечислены в [UPGRADING.md](UPGRADING.md#12-this-builds-commits) (англ.).

### 1. Компилятор и процессор (`ARM Cortex-A53`)
* **Тулчейн OpenWrt GCC 15.2.0** (`CONFIG_GCC_USE_VERSION_15=y`) вместо штатного GCC 14.3 — лучшее планирование инструкций для in-order конвейера Cortex-A53 (сжатый SquashFS меньше на ~241 КБ).
* **Флаги компиляции `-O2 -pipe -mcpu=cortex-a53+crypto+crc`:** официальные сборки используют `-Os`, при котором отключено выравнивание функций, циклов и переходов. У AX3200 128 МБ NAND, поэтому сборка жертвует размером ради скорости (`-O2`) и включает аппаратные инструкции **ARMv8 Crypto (AES, SHA1/SHA2, GHASH)** и **CRC32**.
* **Link-Time Optimization** (`CONFIG_USE_LTO=y`) и **удаление неиспользуемого кода и данных** (`CONFIG_USE_GC_SECTIONS=y`) для пакетов userland.
* **`FORTIFY_SOURCE=2`** (`CONFIG_PKG_FORTIFY_SOURCE_2=y`) вместо уровня 1 по умолчанию. Остальная защита (stack protector для userland и ядра, full RELRO, PIE) и очистка бинарников `sstrip -z` — это умолчания OpenWrt, они оставлены как есть.
* **Регулятор частоты CPU `schedutil`** по умолчанию (`target/linux/mediatek/mt7622/config-6.12`) вместо `ondemand`. `ondemand` периодически опрашивает нагрузку и поднимает частоту (437,5 МГц → 1,35 ГГц) с задержкой при всплесках трафика; `schedutil` управляет частотой напрямую из планировщика задач. Замер на устройстве в простое: загрузка CPU 3,8 % с `schedutil` против 6,0 % с `ondemand`.
* **Регулятор `performance` (по желанию)** держит CPU на 1,35 ГГц постоянно: на мосту Wi-Fi → LAN ему нужно на 28 % меньше CPU на 1 Гбит/с, а задержка по Wi-Fi в простое ниже примерно на 0,2 мс. Но скорость (её ограничивает Wi-Fi) и задержка под нагрузкой не меняются, а роутер греется примерно на 2 °C сильнее, поэтому по умолчанию остаётся `schedutil`. Режимы работы «Максимум скорости», «Низкая задержка» и «SQM» используют `performance`, а отдельно его можно задать в «Расширенных» на той же странице ([Режимы работы](#режимы-работы)); выбор сохраняется при обновлениях. Подробности — в [RESEARCH.md](RESEARCH.md#5-cpu-frequency-governor) (англ.).

### 2. Аппаратное ускорение маршрутизации и Wi-Fi 6 (HFO + WED)
* **Hardware Flow Offloading (PPE):** аппаратный **Packet Processing Engine** MediaTek (`kmod-nft-offload`, `flow_offloading='1'`, `flow_offloading_hw='1'`) выполняет маршрутизацию и NAT установленных соединений аппаратно, на скорости линии и почти без нагрузки на CPU.
* **Wireless Ethernet Dispatch** (`files/etc/modules.conf`: `options mt7915e wed_enable=Y`): ускоренный трафик из WAN передаётся PPE напрямую в DMA-кольца радиомодуля **MT7915E (5 ГГц, Wi-Fi 6)**, минуя CPU. У MT7622 нет WED RX, поэтому так минует CPU только трафик WAN → Wi-Fi; трафик Wi-Fi → WAN пересылает CPU через программное ускорение потоков.
* **Провод → Wi-Fi аппаратно (`bridger`, по умолчанию выключен):** трафик между LAN-портами и клиентами Wi-Fi идёт через мост, а не маршрутизируется, поэтому HFO его не касается и его пересылает CPU: до ~1,2–1,3 Гбит/с к клиенту 5 ГГц, одно ядро при этом на пределе. `bridger` может создавать аппаратное правило для каждой пары хостов, которые обмениваются трафиком, и тогда трафик провод → 5 ГГц пересылают PPE и WED мимо CPU: те же ~1,3 Гбит/с (предел радиоканала) при ~8 % CPU вместо ~70 %. По умолчанию он выключен: как и WED для трафика из интернета, аппаратный путь обходит распределение эфира и очереди mac80211, поэтому задержка выше (поток 200 Мбит/с: пинг 3,0–3,7 мс в медиане вместо 1,7 мс), а несколько активных клиентов делят эфир менее справедливо (три клиента: 580–630 Мбит/с в сумме вместо 790–810, один почти без скорости). Его включает режим работы «Максимум скорости» — для больших передач одному активному клиенту ([Режимы работы](#режимы-работы)). Подробности — в [RESEARCH.md](RESEARCH.md#11-wi-fi--lan-throughput-and-bridger) (англ.).
* **Без WED (по желанию):** без WED весь трафик к клиентам Wi-Fi проходит через распределение эфира mac80211. В домашних тестах (приставка смотрит 4K, игрок по Wi-Fi пингует 50 раз в секунду, поток как у VR) разницы не было; только пока другой клиент Wi-Fi качал на полной скорости, пинг игрока p99 был ниже: ~27 мс вместо ~30 мс, ценой 6–9 пунктов CPU. На гигабитном тарифе CPU тогда может ограничить скорость Wi-Fi. WED выключен в режиме работы «Низкая задержка» ([Режимы работы](#режимы-работы)). Подробности — в [RESEARCH.md](RESEARCH.md#12-several-wi-fi-clients-latency-and-wed) (англ.).
* **Правильная статистика трафика при ускорении:** ускоренный трафик идёт мимо CPU, и статистика по клиентам (`nlbwmon`) раньше теряла его часть или прыгала на ~4 ГБ — например, у соединений, закрытых сразу после передачи, после перезагрузки firewall и при скачивании по Wi-Fi. Исправления ядра приводят её в соответствие с реальным трафиком. Подробности и замеры — в [RESEARCH.md](RESEARCH.md#3-traffic-accounting-with-hardware-offloading) (англ.).
* **Графики интерфейсов при ускорении:** статистика `wan` и `lan1`–`lan3` (графики в *Статистике*, графики реального времени LuCI, `ip -s link`) берётся из счётчиков портов коммутатора (перенесено из Linux 6.16), поэтому показывает реальный трафик. `br-lan` и интерфейсы Wi-Fi по-прежнему показывают только трафик, обработанный CPU.
* **После перезапуска Wi-Fi:** после `wifi down`/`up` (например, по расписанию) интерфейсы точек доступа сами возвращаются во flowtable, так что отдача с беспроводных клиентов по-прежнему идёт быстрым путём.
* HFO обходит очереди Linux, поэтому не совместим с SQM — см. [SQM или аппаратное ускорение?](#sqm-или-аппаратное-ускорение).

### 3. Защита NVRAM от софт-брика («6 перезагрузок → оранжевый индикатор»)
* **Проблема:** новые версии стокового U-Boot при каждой загрузке увеличивают счётчик `flag_try_sys1_failed` в разделе `u-boot-env` (`/dev/mtd3`). После 6 перезагрузок U-Boot переключается на резервный слот прошивки (`system 1`), который OpenWrt перезаписал своим единым UBI-разделом, — роутер «окирпичивается» с горящим оранжевым индикатором.
* **Решение** (`target/linux/mediatek/mt7622/base-files/etc/init.d/bootcount`): при каждой загрузке проверяются значения ниже, и `fw_setenv` вызывается только для отличающихся (без лишних записей во флеш):
  * `flag_try_sys1_failed=0`, `flag_try_sys2_failed=0`, `flag_boot_rootfs=0`, `flag_boot_success=1`, `flag_last_success=1`, `boot_fw1="run boot_rd_img;bootm"` — собственно защита от брика;
  * `boot_wait=on` и `uart_en=1` — сохраняют возможность восстановления по TFTP и через последовательную консоль U-Boot. Для обоих нужен физический доступ к роутеру.
  * `ssh_en` (используется только стоковой прошивкой) не трогается.

### 4. Настройки Wi-Fi по умолчанию (`77_wireless`)
* **Надёжное обнаружение 5 ГГц при первом старте:** `77_wireless` вызывает `/sbin/wifi config` перед настройкой радио, поэтому PCIe-модуль `mt7915e` попадает в `/etc/config/wireless`, даже если драйвер инициализировался с задержкой.
* `radio0` — встроенный в SoC радиомодуль **2,4 ГГц (802.11n)**, `radio1` — PCIe-модуль **5 ГГц MT7915E (802.11ax)**. Каждый настраивается по своему диапазону (`band`):
  * **Регион:** страна `PA` для обоих модулей (`CONFIG_PACKAGE_MAC80211_COUNTRY="PA"`). Она разрешает больше каналов и большую мощность передатчика, чем многие другие регионы; если этого требует местное законодательство, укажите свою страну в LuCI.
  * **2,4 ГГц:** `HT20`, канал `1`, WPA2 (`psk2+ccmp`) — максимальная совместимость с IoT.
  * **5 ГГц:** `HE80` на канале `36` без DFS (нет отключений на 1–10 минут из-за поиска радаров), `noscan='1'` (сеть не сужает канал из-за соседних сетей), смешанный режим WPA2/WPA3 (`sae-mixed`) с `ocv='0'` (совместимость клиентов с SAE), режим WNM-Sleep (`wnm_sleep_mode='1'`, `wnm_sleep_mode_no_keys='1'`) и `dtim_period='3'`: телефоны дольше спят и меньше расходуют батарею.
  * **Имена сетей:** `<плата>-<диапазон>-<номер радио><последние 4 hex-цифры MAC>`, например `redmi-router-ax6s-2g-0a1b2` и `redmi-router-ax6s-5g-1a1b2`; пароль **`12345678`**.
* Настройки применяются, только если у радио ещё нет ключа Wi-Fi, поэтому восстановленная конфигурация не перезаписывается.
* **Полный `wpad-mbedtls`** вместо `wpad-basic-mbedtls`, который OpenWrt ставит на этот роутер по умолчанию. Базовый вариант уже поддерживает WPA3 (SAE), 802.11r и 802.11k; полный добавляет 802.11v (WNM), без которого не работает режим WNM-Sleep из настроек 5 ГГц выше, а также WPS, WPA2/WPA3-Enterprise (802.1X, встроенный RADIUS-сервер), mesh 802.11s и Wi-Fi Easy Connect (DPP). Быстрый роуминг (802.11k/v/r) выключен, как и в штатной OpenWrt: он нужен, только когда несколько точек доступа раздают одну сеть (один SSID). Для такой сети включите его в настройках беспроводной сети и установите `usteer` (`apk add usteer luci-app-usteer`).
* **Исправления драйвера Wi-Fi из ветки разработки mt76** (18 исправлений поверх mt76 из OpenWrt 25.12): падения ядра при подключении и отключении клиентов и при восстановлении прошивки радиомодуля, агрегация трафика с приоритетом «голос» на 5 ГГц, правильные параметры HE DCM / VHT STBC клиентов. На 2,4 ГГц снова работает адаптивная чувствительность (SCS) MT7622 (из-за ошибки в драйвере она с 2022 года оставалась на заводском значении): на загруженном канале 2,4 ГГц тестового стенда доля времени, когда радио считает канал занятым, упала вдвое (31 → 15 %), потери ping до клиентов уменьшились. Порог никогда не поднимается выше сигнала самого слабого подключённого клиента. Подробности — в [RESEARCH.md](RESEARCH.md#10-wi-fi-driver-fixes-from-mt76-master) (англ.).

### 5. Сетевой стек и память (256 МБ RAM)
* **Packet steering, режим 2** (`packet_steering='2'`, *Включено (все процессоры)*, `steering_flows='128'`): закрепляет потоки NAPI драйверов Ethernet (`mtk_eth`) и Wi-Fi (`mt76`) за разными ядрами CPU, распределяет RPS по обоим ядрам и включает RFS на 128 потоков. По сравнению с режимом 1 он даёт на 6–11 % больше скорости провод → Wi-Fi клиенту, принимающему больше ~1,2 Гбит/с, и ровнее делит нагрузку между ядрами, а задержка в домашних тестах та же ([RESEARCH.md](RESEARCH.md#13-packet-steering-mode-2-and-the-operating-modes), англ.). Режим работы «SQM» использует режим 1: с CAKE ему нужно меньше CPU ([RESEARCH.md](RESEARCH.md#9-wan-bufferbloat-and-the-need-for-sqm), англ.). `irqbalance` не установлен: он перемещает только прерывания, а не потоки NAPI, которые обрабатывают пакеты, поэтому может развести прерывания Ethernet и их поток NAPI по разным ядрам; на устройстве он ничего не дал ([RESEARCH.md](RESEARCH.md#1-irqbalance-vs-packet-steering), англ.). При желании его можно установить командой `apk add irqbalance`.
* **Настройки sysctl** (`files/etc/sysctl.d/99-bbr.conf`):
  * **TCP BBR**, `fq_codel` и TCP Fast Open (`tcp_fastopen=3`). Они действуют на TCP-соединения самого роутера (LuCI, DoH-прокси, сервер `iperf3`, загрузка пакетов), а не на трафик клиентов LAN, который роутер пересылает. `fq_codel` и так является дисциплиной очередей по умолчанию в OpenWrt.
  * Увеличенная таблица conntrack (`nf_conntrack_max=32768`) и скорректированные таймауты TCP/UDP для P2P и игр.
  * Глобальная таблица потоков RFS (`net.core.rps_sock_flow_entries=1024`). Packet steering в OpenWrt задаёт только число потоков на очередь (`steering_flows`); без этой таблицы RFS не работает. Влияет только на трафик, который завершается на самом роутере.
* **«Стелс»-файрвол:** политики `input`/`forward` по умолчанию и в зоне `wan` — `DROP` вместо `REJECT`, плюс `drop_invalid='1'`. SSH (`dropbear`) слушает только интерфейс LAN (`Interface='lan'`).
* **NTP-сервер для LAN** (`system.ntp.enable_server='1'`).
* **`zram-swap` на 120 МБ с `lz4`** (`CONFIG_KERNEL_ZRAM_DEF_COMP_LZ4=y`) и `vm.swappiness=100`, `vm.page-cluster=0`, `vm.vfs_cache_pressure=50`.
* **Службы перезапускаются бесконечно** после сбоев (procd `respawn_retry='0'`); `https-dns-proxy` переживает переподключения WAN (`conn_loss_time='30'`).

### 6. Как применяются настройки (`99-custom-settings`)
Скрипты `uci-defaults` выполняются при первой загрузке после **каждой** прошивки, в том числе после sysupgrade с сохранением настроек. `files/etc/uci-defaults/99-custom-settings` применяет настройки из разделов 2 и 5, а также настройки DoH, статистики, автозапуска DDNS и темы LuCI (см. [Предустановленные пакеты](#предустановленные-пакеты)) **один раз для конфигурации** и сохраняет маркер в `/etc/config/ax3200`. Поэтому ваши изменения (например, HFO, выключенный ради SQM) сохраняются при обновлениях. При каждой прошивке выполняется только удаление подключаемого конфига collectd из прежних сборок. Две более поздние настройки тоже применяются один раз к конфигурациям, обновлённым с прежних сборок: выключенный `bridger` и режим 2 packet steering вместо режима 1 (если SQM не включён). Список тем LuCI приводится в соответствие с установленными темами при каждой загрузке (`files/etc/init.d/luci-themes`), поэтому это работает и после восстановления архива настроек, сделанного на другой прошивке. Чтобы применить настройки сборки заново:
```sh
uci -q delete ax3200.defaults && uci commit ax3200
sh /rom/etc/uci-defaults/99-custom-settings
reboot
```

### 7. Совместимость с официальным репозиторием (`vermagic` + `apk`)
* `vermagic_update.sh` загружает `vermagic` ядра официального релиза OpenWrt 25.12.6 (`685dcedeed3538a4cc670fc3fd59eac1`), а `scripts/getvermagic.sh` собирает ядро с ним, поэтому пакеты `kmod-*` из официального репозитория устанавливаются без ошибок несовпадения `vermagic`.
* **Конфигурация ядра совпадает с официальной.** Одного совпадения `vermagic` недостаточно: официальный модуль работает корректно, только если у всех структур ядра, которые он использует, одинаковая раскладка. Официальный buildbot собирает с `CONFIG_ALL_KMODS=y` и без `KALLSYMS`, а это меняет `struct module`, `net_device`, `struct net` и `sk_buff`. Эта сборка делает так же (`CONFIG_ALL_KMODS=y`, `# CONFIG_KERNEL_KALLSYMS is not set`), поэтому её `.config` ядра отличается от официального из SDK только версией GCC, регулятором частоты `schedutil` по умолчанию и бэкендами сжатия zram — ни одно из этих отличий не затрагивает ABI модулей.
* **Проверено на устройстве:** официальные `kmod-dummy` и `kmod-wireguard` (вместе с NEON-ускоренными модулями ChaCha20/Poly1305) загружаются и работают; через туннель WireGuard прошло около 2 ГиБ на скорости 530–600 Мбит/с без ошибок ядра.
* `ALL_KMODS` лишь собирает все модули ядра в `bin/`; в прошивку попадают только выбранные. Без `KALLSYMS` ядро меньше примерно на 260 КиБ во флеше и на 0,7 МиБ в RAM, а в трассировках падения ядра вместо имён функций выводятся адреса (как в официальных образах).
* Пакеты управляются штатным для OpenWrt 25.12 менеджером **`apk`** (`apk-mbedtls`) и `luci-app-package-manager`.

## Режимы работы

Лучшие настройки ускорения зависят от того, как используется роутер. LuCI → *Система → Режим работы* (`luci-app-tuning`, пакет этой сборки) задаёт их вместе — режимами, проверенными на этом роутере ([RESEARCH.md](RESEARCH.md#13-packet-steering-mode-2-and-the-operating-modes), англ.): тип ускорения потоков, WED, `bridger`, packet steering, регулятор частоты CPU и SQM. Для каждого режима указано, кому он подходит, плюсы и минусы с измеренными цифрами и предупреждения.

| Режим | Для кого | Настройки |
|---|---|---|
| **Сбалансированный** (по умолчанию) | Обычный дом: телефоны, ТВ, ноутбуки, игры, тариф до 1 Гбит/с. | аппаратный NAT и WED, `bridger` выкл, packet steering 2, `schedutil` |
| **Максимум скорости** | Большие копирования с проводного NAS или ПК на одно устройство Wi-Fi: ~1,3 Гбит/с при ~8 % CPU вместо ~70 %. Не для VR и игр: задержка выше, эфир делится менее справедливо. | как «Сбалансированный», плюс `bridger` и `performance` |
| **Низкая задержка** | VR-стриминг с проводного ПК, игры по Wi-Fi: чуть ниже пики задержки, пока другое устройство качает (p99 ~27 вместо ~30 мс). Загрузки из интернета на Wi-Fi нагружают CPU сильнее. | как «Сбалансированный», но WED выкл и `performance` |
| **SQM (медленный канал)** | Каналы медленнее ~300 Мбит/с, у которых задержка сильно растёт под нагрузкой ([SQM или аппаратное ускорение?](#sqm-или-аппаратное-ускорение)). | программное ускорение потоков, CAKE на WAN, WED выкл, packet steering 1, `performance` |
| **Ручной** | Любое сочетание настроек в «Расширенных». | |

* Применение режима перезагружает роутер: WED меняется только при загрузке.
* Страница показывает режим, которому соответствуют текущие настройки; после изменений на других страницах — «Ручной».
* Режим сохраняется при обновлении прошивки.

## Обновления прошивки

Начиная с r10 роутер сам ищет новые версии этой сборки на GitHub. Когда выходит новая версия, на странице «Обзор» появляется уведомление. LuCI → *Система → Обновления сборки AX3200 / AX6S* показывает, что изменилось, и устанавливает обновление одной кнопкой — с сохранением настроек или без. Перед установкой роутер проверяет, что файл скачан целиком и подходит этому роутеру. Некоторые версии так установить нельзя, например если меняется разметка флеш-памяти: тогда страница объясняет почему и даёт ссылку на инструкцию. Проверку можно выключить или задать другой интервал на той же странице.

Это стандартное поведение OpenWrt: при обновлении пакеты, которые вы устанавливали сами, удаляются. С галочкой **«Сохранить мои пакеты»** рядом с кнопкой обновления (включена по умолчанию) роутер после обновления, как только подключится к интернету, сам установит их снова и повторит замены пакетов прошивки, например `dnsmasq-full` вместо `dnsmasq`; выключенные вами службы останутся выключенными. Пакеты, установленные не из репозитория (файлом или скриптом установки), нужно установить заново вручную: страница покажет их список. После установки пакетов роутер один раз перезагружается, чтобы они запустились как после обычной загрузки. При обновлении другим способом (*Восстановление / Обновление*, `sysupgrade`) пакеты не восстанавливаются.

Attended Sysupgrade, собственное средство обновления OpenWrt, в сборку не входит. Его можно установить самостоятельно, и обновление через него сработает, но роутер перейдёт на обычную OpenWrt без преимуществ этой сборки.

## SQM или аппаратное ускорение?

**SQM** (`luci-app-sqm`, CAKE) борется с **bufferbloat** — ростом задержек при полной загрузке канала (звонки, игры и сайты начинают тормозить, когда что-то качается или отдаётся). Ему нужно видеть каждый пакет. **Аппаратное ускорение (HFO)** переносит установленные соединения в PPE мимо очередей Linux, поэтому **при включённом HFO SQM ничего не делает**. Без HFO не работает и WED, и весь маршрутизируемый трафик и трафик Wi-Fi обрабатывает CPU.

| | HFO + WED (по умолчанию) | SQM (CAKE) |
|---|---|---|
| Максимальная скорость маршрутизации | ~1 Гбит/с, CPU почти не нагружен | ограничена CPU: по замерам ~400 Мбит/с для проводных клиентов и ~230–250 Мбит/с для клиентов 5 ГГц, одно ядро при этом на пределе ([RESEARCH.md](RESEARCH.md#9-wan-bufferbloat-and-the-need-for-sqm), англ.) |
| Задержка под нагрузкой | зависит от буферов провайдера/модема | низкая и стабильная |
| Когда лучше | быстрые каналы (≳ 500 Мбит/с), каналы без bufferbloat | медленные или асимметричные каналы: DSL, LTE/5G, кабельный интернет, PPPoE ниже ~300–500 Мбит/с |

**Как выбрать:** с настройками по умолчанию запустите тест bufferbloat (например, Waveform «Bufferbloat Test») по кабелю. Если задержка под нагрузкой остаётся низкой (оценка A/B), оставьте HFO. Если она вырастает на десятки или сотни миллисекунд, а тариф ниже ~300 Мбит/с, переходите на SQM.

**Переход на SQM:** LuCI → *Система → Режим работы* → **SQM (медленный канал)**, укажите скорости скачивания и отдачи (~85–95 % от измеренных без SQM) и нажмите *Применить*; роутер перезагрузится. Затем повторите тест. Режим меняет аппаратное ускорение на программное, которое на этом роутере работает вместе с SQM с той же скоростью и задержкой, и включает CAKE на WAN с указанными скоростями. Остальные параметры SQM, например накладные расходы канального уровня для DSL, по-прежнему задаются в LuCI → *Сеть → Умное управление очередью* (SQM QoS).

**Возврат к HFO:** выберите «Сбалансированный».

Выбор сохраняется при sysupgrade (см. [раздел 6](#6-как-применяются-настройки-99-custom-settings)).

## Wi-Fi 160 МГц (HE160) и VR-стриминг

Радиомодуль 5 ГГц по умолчанию работает в режиме **HE80 на канале 36** — так сеть видят максимально разные клиенты. MT7915E поддерживает и **160 МГц (HE160)**: для обычных клиентов 2×2 (телефоны, ноутбуки, VR-шлемы) это вдвое более высокая скорость канала — до 2402 Мбит/с вместо 1201 Мбит/с. На 160 МГц радиомодуль использует 2 пространственных потока вместо 4, поэтому клиенты 3×3/4×4 выигрывают меньше.

В регионе `PA` диапазон 5470–5725 МГц (каналы 100–128) разрешает 160 МГц **без DFS**: нет минутной проверки канала после загрузки и переключений из-за радара.

Компромиссы:
* клиенты без поддержки каналов 100–144 не увидят сеть 5 ГГц;
* немного меньше дальность на краю зоны покрытия (та же мощность распределяется на вдвое более широкую полосу);
* вне Панамы на этих каналах обычно действуют правила DFS — проверьте местное законодательство.

Включение: LuCI → *Сеть → Беспроводная сеть* → радиомодуль 5 ГГц → *Изменить* → *Настройка частоты*: режим **AX**, канал **100**, ширина **160 МГц** → *Сохранить и применить*, или по SSH:
```sh
uci set wireless.radio1.channel='100'
uci set wireless.radio1.htmode='HE160'
uci commit wireless
wifi reload
```
После этого `iwinfo wl1-ap0 info` показывает `HT Mode: HE160`. Чтобы вернуть умолчание, задайте канал `36` и `HE80`.

**PC VR-стриминг** (Virtual Desktop, Steam Link, Air Link) выигрывает от HE160 больше всего — при условии, что шлем поддерживает 160 МГц на 5 ГГц (проверьте его характеристики; поддержка зависит от модели и прошивки):
* подключите ПК к LAN-порту кабелем, чтобы беспроводной участок был один;
* держите шлем в одной комнате с роутером, лучше в прямой видимости;
* подключайте шлем только к сети 5 ГГц;
* используйте режим работы «Сбалансированный» или «Низкая задержка», но не «Максимум скорости»: он повышает задержку потока ([Режимы работы](#режимы-работы));
* во время игры избегайте больших загрузок на другие устройства 5 ГГц: обычный вечер (приставка с 4K, телефоны) на поток не влиял, а загрузка на полной скорости на другой клиент поднимала его задержку p99 с 6–11 мс до 50–100 мс при любых настройках.

Замеры с ноутбуком 2×2 HE160 в роли шлема примерно в 1 м от роутера (канальная скорость 1815–2402 Мбит/с) и проводным ПК как источником: поток UDP 200 Мбит/с, как у VR, терял 0,01–0,15 % пакетов, пинг 1,6–1,8 мс в медиане и 6–11 мс p99, в том числе рядом с приставкой, которая смотрит 4K из интернета. Провод → Wi-Fi до 1,25–1,35 Гбит/с, Wi-Fi → провод 1,5–1,8 Гбит/с ([RESEARCH.md](RESEARCH.md#12-several-wi-fi-clients-latency-and-wed), англ.).

## Предустановленные пакеты
* **Веб-интерфейс:** `luci`, `luci-ssl`, полная русская и английская локализация (`CONFIG_LUCI_LANG_ru=y`; язык выбирается по браузеру). Темы: **Footstrap** (по умолчанию) — новая тема LuCI со сворачиваемой боковой или верхней панелью, светлым и тёмным режимами, поиском по меню и страницей *Appearance* для настройки цветов, плотности, раскладки и обоев — и штатная **Bootstrap**. После обновления со старой сборки или восстановления архива настроек, сделанного на другой прошивке, Footstrap снова появляется в списке тем, а удалённая тема (OpenWrt-2020, Material) автоматически заменяется на Footstrap.
* **Шифрованный DNS (DoH, HTTP/2 и HTTP/3):** `https-dns-proxy` + `luci-app-https-dns-proxy` (Cloudflare и Google из коробки). Клиентов не заставляют пользоваться DNS роутера (`force_dns='0'`), поэтому шифрованный DNS на устройствах, например «Частный DNS» (DoT) на Android, продолжает работать.
* **SQM / CAKE QoS:** `luci-app-sqm` (`sqm-scripts`, `kmod-sched-cake`) — установлен, но по умолчанию **выключен**; его настраивает режим работы «SQM».
* **Домашние сервисы:**
  * `luci-app-upnp` (`miniupnpd-nftables`), `luci-app-wol` (`etherwake`), `luci-app-watchcat`, `luci-app-wifischedule`, `luci-app-uhttpd`;
  * `luci-app-ddns`: автозапуск выключен, пока не включена ни одна служба DDNS (настройте службу и нажмите *Службы → Динамический DNS → Запустить DDNS*). С исправлением LuCI ([openwrt/luci#9154](https://github.com/openwrt/luci/pull/9154)): без интернета статус DDNS больше не оставляет «Обзор» в LuCI пустым на 10 секунд за каждую службу;
  * `luci-app-tuning`: режимы работы (*Система → Режим работы*), пакет этой сборки из `package/ax3200/`. Заменяет `luci-app-cpufreq` прежних сборок: регулятор частоты CPU задаётся на той же странице;
  * `luci-app-fwupdate`: обновления прошивки (*Система → Обновления сборки AX3200 / AX6S*), пакет этой сборки из `package/ax3200/`;
  * `bridger`: трафик провод → Wi-Fi аппаратно, по умолчанию выключен, его включает режим «Максимум скорости» ([раздел 2](#2-аппаратное-ускорение-маршрутизации-и-wi-fi-6-hfo--wed)).
* **Мониторинг и диагностика:** `luci-app-nlbwmon` (учёт трафика по клиентам), `luci-app-statistics` (графики `collectd`: загрузка и частота CPU, RAM, `br-lan`/`wan`, Wi-Fi, conntrack, аппаратные датчики и температура MT7915E; график `wan` учитывает и ускоренный трафик, см. [Графики интерфейсов при ускорении](#2-аппаратное-ускорение-маршрутизации-и-wi-fi-6-hfo--wed)), `luci-app-ttyd` (терминал в браузере), консольные утилиты `htop`, `nano`, `curl`, `iperf3`, `ethtool`, `tcpdump-mini`, `bind-dig`, `mtr-nojson`.

## О проекте OpenWrt

OpenWrt — операционная система на базе Linux для встраиваемых устройств. Вместо одной статичной прошивки OpenWrt предоставляет полностью записываемую файловую систему с менеджером пакетов. Это освобождает от набора приложений и настроек производителя и позволяет настроить устройство под любую задачу с помощью пакетов. Для разработчиков OpenWrt — это платформа для создания приложений без необходимости собирать вокруг них целую прошивку; для пользователей — возможность полной настройки и применения устройства так, как производитель и не предполагал.
