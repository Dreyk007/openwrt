# OpenWrt 25.12 (`xq-25.12`) — оптимизированная сборка для Xiaomi AX3200 / Redmi AX6S

Этот репозиторий (ветка **`xq-25.12`**) — форк стабильного релиза **OpenWrt 25.12.6** (`Linux 6.12.112`), адаптированный для **Xiaomi Router AX3200 (RB01) / Redmi Router AX6S (RB03)** на платформе **MediaTek MT7622B + MT7531BE + MT7915E** (включает доработки MediaTek из дерева `remittor`).

Цель сборки — **гигабит по кабелю и Wi-Fi 6 на полной скорости, низкие задержки, защита NVRAM загрузчика от «окирпичивания» и полный набор функций домашнего роутера «из коробки»** при сохранении совместимости с официальным репозиторием пакетов OpenWrt.

> [!WARNING]
> Wi-Fi **включается при первом старте с общеизвестным паролем `12345678`**, а у веб-интерфейса **нет пароля root**. Задайте оба сразу после прошивки (LuCI → *Система → Администрирование* и *Сеть → Беспроводная сеть*).

## Основные изменения

### 1. Компилятор и процессор (`ARM Cortex-A53`)
* **Тулчейн OpenWrt GCC 15.2.0** (`CONFIG_GCC_USE_VERSION_15=y`) вместо штатного GCC 14.3 — лучшее планирование инструкций для in-order конвейера Cortex-A53 (сжатый SquashFS меньше на ~241 КБ).
* **Флаги компиляции `-O2 -pipe -mcpu=cortex-a53+crypto+crc`:** официальные сборки используют `-Os`, при котором отключено выравнивание функций, циклов и переходов. У AX3200 128 МБ NAND, поэтому сборка жертвует размером ради скорости (`-O2`) и включает аппаратные инструкции **ARMv8 Crypto (AES, SHA1/SHA2, GHASH)** и **CRC32**.
* **Link-Time Optimization** (`CONFIG_USE_LTO=y`) и **удаление неиспользуемого кода и данных** (`CONFIG_USE_GC_SECTIONS=y`) для пакетов userland.
* **`FORTIFY_SOURCE=2`** (`CONFIG_PKG_FORTIFY_SOURCE_2=y`) вместо уровня 1 по умолчанию. Остальная защита (stack protector для userland и ядра, full RELRO, PIE) и очистка бинарников `sstrip -z` — это умолчания OpenWrt, они оставлены как есть.
* **Регулятор частоты CPU `schedutil`** по умолчанию (`target/linux/mediatek/mt7622/config-6.12`) вместо `ondemand`. `ondemand` периодически опрашивает нагрузку и поднимает частоту (300 МГц → 1,35 ГГц) с задержкой при всплесках трафика; `schedutil` управляет частотой напрямую из планировщика задач.

### 2. Аппаратное ускорение маршрутизации и Wi-Fi 6 (HFO + WED)
* **Hardware Flow Offloading (PPE):** аппаратный **Packet Processing Engine** MediaTek (`kmod-nft-offload`, `flow_offloading='1'`, `flow_offloading_hw='1'`) выполняет маршрутизацию и NAT установленных соединений аппаратно, на скорости линии и почти без нагрузки на CPU.
* **Wireless Ethernet Dispatch** (`files/etc/modules.conf`: `options mt7915e wed_enable=Y`): ускоренный трафик из WAN передаётся PPE напрямую в DMA-кольца радиомодуля **MT7915E (5 ГГц, Wi-Fi 6)**, минуя CPU.
* **`bridger` не включён:** он полезен только в режиме «тупой» точки доступа. В режиме роутера HFO + WED уже ускоряют трафик WAN ↔ LAN/Wi-Fi, а `bridger` может вызывать кратковременные зависания клиентов при роуминге 802.11k/v/r и конфликтует с фильтрами `tc`/`nftables`.
* HFO обходит очереди Linux, поэтому не совместим с SQM — см. [SQM или аппаратное ускорение?](#sqm-или-аппаратное-ускорение).

### 3. Защита NVRAM от софт-брика («6 перезагрузок → оранжевый индикатор»)
* **Проблема:** новые версии стокового U-Boot при каждой загрузке увеличивают счётчик `flag_try_sys1_failed` в разделе `u-boot-env` (`/dev/mtd3`). После 6 перезагрузок U-Boot переключается на резервный слот прошивки (`system 1`), который OpenWrt перезаписал своим единым UBI-разделом, — роутер «окирпичивается» с горящим оранжевым индикатором.
* **Решение** (`target/linux/mediatek/mt7622/base-files/etc/init.d/bootcount`): при каждой загрузке проверяются значения ниже, и `fw_setenv` вызывается только для отличающихся (без лишних записей во флеш):
  * `flag_try_sys1_failed=0`, `flag_try_sys2_failed=0`, `flag_boot_rootfs=0`, `flag_boot_success=1`, `flag_last_success=1`, `boot_fw1="run boot_rd_img;bootm"` — собственно защита от брика;
  * `boot_wait=on` и `uart_en=1` — сохраняют возможность восстановления по TFTP и через последовательную консоль U-Boot. Для обоих нужен физический доступ к роутеру.
  * `ssh_en` (используется только стоковой прошивкой) не трогается.

### 4. Настройки Wi-Fi по умолчанию (`77_wireless`)
* **Надёжное обнаружение 5 ГГц при первом старте:** `77_wireless` вызывает `/sbin/wifi config` перед настройкой радио, поэтому PCIe-модуль `mt7915e` попадает в `/etc/config/wireless`, даже если драйвер инициализировался с задержкой.
* `radio0` — встроенный в SoC радиомодуль **2,4 ГГц (802.11n)**, `radio1` — PCIe-модуль **5 ГГц MT7915E (802.11ax)**. Каждый настраивается по своему диапазону (`band`):
  * **Регион:** страна `PA` для обоих модулей (`CONFIG_PACKAGE_MAC80211_COUNTRY="PA"`). Она разрешает больше каналов и большую мощность передатчика, чем многие другие регионы; если этого требует местное законодательство, укажите свою страну в LuCI.
  * **2,4 ГГц:** `HT20`, канал `1`, WPA2 (`psk2+ccmp`) — максимальная совместимость с IoT.
  * **5 ГГц:** `HE80`, канал `36` без DFS (нет отключений на 1–10 минут из-за поиска радаров), `noscan='1'`, смешанный режим WPA2/WPA3 (`sae-mixed`), `wnm_sleep_mode='1'`, `wnm_sleep_mode_no_keys='1'`, `dtim_period='3'`, `ocv='0'` (совместимость клиентов с SAE).
  * **Имена сетей:** `<плата>-<диапазон>-<номер радио><последние 4 hex-цифры MAC>`, например `redmi-router-ax6s-2g-0a1b2` и `redmi-router-ax6s-5g-1a1b2`; пароль **`12345678`**.
* Настройки применяются, только если у радио ещё нет ключа Wi-Fi, поэтому восстановленная конфигурация не перезаписывается.
* **Полный `wpad-mbedtls`** вместо урезанного `basic`: **WPA3 (SAE)** и быстрый роуминг **802.11k/v/r** (+ `usteer`).

### 5. Сетевой стек и память (256 МБ RAM)
* **Packet steering** (`packet_steering='1'`, `steering_flows='128'`): закрепляет потоки NAPI драйверов Ethernet (`mtk_eth`) и Wi-Fi (`mt76`) за разными ядрами CPU и включает RPS + RFS на 128 потоков. `irqbalance` намеренно не установлен: при потоковом NAPI обработка пакетов идёт в потоках, которые packet steering уже распределяет, а irqbalance перемещает только верхние половины прерываний — не зная, где закреплены эти потоки, поэтому может развести прерывания TX/RX Ethernet на другое ядро, чем их поток NAPI. При желании его можно установить командой `apk add irqbalance`.
* **Настройки sysctl** (`files/etc/sysctl.d/99-bbr.conf`):
  * **TCP BBR**, `fq_codel` и TCP Fast Open (`tcp_fastopen=3`). Они действуют на TCP-соединения самого роутера (LuCI, DoH-прокси, сервер `iperf3`, загрузка пакетов), а не на трафик клиентов LAN, который роутер пересылает. `fq_codel` и так является дисциплиной очередей по умолчанию в OpenWrt.
  * Увеличенная таблица conntrack (`nf_conntrack_max=32768`) и скорректированные таймауты TCP/UDP для P2P и игр.
  * Глобальная таблица потоков RFS (`net.core.rps_sock_flow_entries=1024`). Packet steering в OpenWrt задаёт только число потоков на очередь (`steering_flows`); без этой таблицы RFS не работает. Влияет только на трафик, который завершается на самом роутере.
* **«Стелс»-файрвол:** политики `input`/`forward` по умолчанию и в зоне `wan` — `DROP` вместо `REJECT`, плюс `drop_invalid='1'`. SSH (`dropbear`) слушает только интерфейс LAN (`Interface='lan'`).
* **NTP-сервер для LAN** (`system.ntp.enable_server='1'`).
* **`zram-swap` на 120 МБ с `lz4`** (`CONFIG_KERNEL_ZRAM_DEF_COMP_LZ4=y`) и `vm.swappiness=100`, `vm.page-cluster=0`, `vm.vfs_cache_pressure=50`.
* **Службы перезапускаются бесконечно** после сбоев (procd `respawn_retry='0'`); `https-dns-proxy` переживает переподключения WAN (`conn_loss_time='30'`).

### 6. Как применяются настройки (`99-custom-settings`)
Скрипты `uci-defaults` выполняются при первой загрузке после **каждой** прошивки, в том числе после sysupgrade с сохранением настроек. `files/etc/uci-defaults/99-custom-settings` применяет настройки из разделов 2 и 5, а также настройки DoH, статистики и темы LuCI (см. [Предустановленные пакеты](#предустановленные-пакеты)) **один раз для конфигурации** и сохраняет маркер в `/etc/config/ax3200`. Поэтому ваши изменения (например, HFO, выключенный ради SQM) сохраняются при обновлениях. При каждой прошивке выполняется только миграция тем LuCI (удаление записей об удалённых темах). Чтобы применить настройки сборки заново:
```sh
uci -q delete ax3200.defaults && uci commit ax3200
sh /rom/etc/uci-defaults/99-custom-settings
reboot
```

### 7. Совместимость с официальным репозиторием (`vermagic` + `apk`)
* `vermagic_update.sh` загружает `vermagic` ядра официального релиза OpenWrt 25.12.6 (`685dcedeed3538a4cc670fc3fd59eac1`), а `scripts/getvermagic.sh` собирает ядро с ним, поэтому пакеты `kmod-*` из официального репозитория устанавливаются без ошибок несовпадения `vermagic`.
* **Конфигурация ядра совпадает с официальной.** Одного совпадения `vermagic` недостаточно: официальный модуль работает корректно, только если у всех структур ядра, которые он использует, одинаковая раскладка. Официальный buildbot собирает с `CONFIG_ALL_KMODS=y` и без `KALLSYMS`, а это меняет `struct module`, `net_device`, `struct net` и `sk_buff`. Эта сборка делает так же (`CONFIG_ALL_KMODS=y`, `# CONFIG_KERNEL_KALLSYMS is not set`), поэтому её `.config` ядра отличается от официального из SDK только версией GCC, регулятором частоты `schedutil` по умолчанию и бэкендами сжатия zram — ни одно из этих отличий не затрагивает ABI модулей.
* **Проверено на устройстве:** официальные `kmod-dummy` и `kmod-wireguard` (вместе с NEON-ускоренными модулями ChaCha20/Poly1305) загружаются и работают; через туннель WireGuard прошло около 2 ГиБ на скорости 530–600 Мбит/с без ошибок ядра.
* `ALL_KMODS` лишь собирает все модули ядра в `bin/`; в прошивку попадают только выбранные. Без `KALLSYMS` ядро меньше примерно на 260 КиБ во флеше и на 0,7 МиБ в RAM, а в трассировках падения ядра вместо имён функций выводятся адреса (как в официальных образах).
* Пакеты управляются штатным для OpenWrt 25.12 менеджером **`apk`** (`apk-mbedtls`) и `luci-app-package-manager`.

## SQM или аппаратное ускорение?

**SQM** (`luci-app-sqm`, CAKE) борется с **bufferbloat** — ростом задержек при полной загрузке канала (звонки, игры и сайты начинают тормозить, когда что-то качается или отдаётся). Ему нужно видеть каждый пакет. **Аппаратное ускорение (HFO)** переносит установленные соединения в PPE мимо очередей Linux, поэтому **при включённом HFO SQM ничего не делает**. Без HFO не работает и WED, и весь маршрутизируемый трафик и трафик Wi-Fi обрабатывает CPU.

| | HFO + WED (по умолчанию) | SQM (CAKE) |
|---|---|---|
| Максимальная скорость маршрутизации | ~1 Гбит/с, CPU почти не нагружен | ограничена CPU; для MT7622 с CAKE пользователи сообщают примерно о 500–600 Мбит/с |
| Задержка под нагрузкой | зависит от буферов провайдера/модема | низкая и стабильная |
| Когда лучше | быстрые каналы (≳ 500 Мбит/с), каналы без bufferbloat | медленные или асимметричные каналы: DSL, LTE/5G, кабельный интернет, PPPoE ниже ~300–500 Мбит/с |

**Как выбрать:** с настройками по умолчанию запустите тест bufferbloat (например, Waveform «Bufferbloat Test») по кабелю. Если задержка под нагрузкой остаётся низкой (оценка A/B), оставьте HFO. Если она вырастает на десятки или сотни миллисекунд, а тариф ниже ~500 Мбит/с, переходите на SQM.

**Переход на SQM:**
1. LuCI → *Сеть → Межсетевой экран → Основные настройки* → *Ускорение маршрутизации/NAT* → *Тип ускорения потоков*: выберите **Отсутствует** (или **Программное ускорение**; по отзывам, оно обычно уживается с SQM — проверьте, что счётчики CAKE у `ifb4…` и WAN-устройства в `tc -s qdisc` растут под нагрузкой). *Сохранить и применить*.
2. LuCI → *Сеть → Умное управление очередью* (SQM QoS): включите на WAN-интерфейсе (`wan` или `pppoe-wan` для PPPoE), дисциплина `cake`, скрипт `piece_of_cake.qos`, скорости загрузки и отдачи — ~85–95 % от измеренных без SQM. *Сохранить и применить*, затем повторите тест.

**Возврат к HFO:** выключите SQM и снова выберите *Тип ускорения потоков* → **Аппаратное ускорение**.

Выбор сохраняется при sysupgrade (см. [раздел 6](#6-как-применяются-настройки-99-custom-settings)).

## Предустановленные пакеты
* **Веб-интерфейс:** `luci`, `luci-ssl`, полная русская и английская локализация (`CONFIG_LUCI_LANG_ru=y`; язык выбирается по браузеру). Темы: **Footstrap** (по умолчанию) — новая тема LuCI со сворачиваемой боковой или верхней панелью, светлым и тёмным режимами, поиском по меню и страницей *Appearance* для настройки цветов, плотности, раскладки и обоев — и штатная **Bootstrap**. При обновлении со старой сборки удалённая тема (OpenWrt-2020, Material) автоматически заменяется на Footstrap.
* **Шифрованный DNS (DoH, HTTP/2 и HTTP/3):** `https-dns-proxy` + `luci-app-https-dns-proxy` (Cloudflare и Google из коробки). Клиентов не заставляют пользоваться DNS роутера (`force_dns='0'`), поэтому шифрованный DNS на устройствах, например «Частный DNS» (DoT) на Android, продолжает работать.
* **SQM / CAKE QoS:** `luci-app-sqm` (`sqm-scripts`, `kmod-sched-cake`) — установлен, но по умолчанию **выключен**.
* **Домашние сервисы:** `luci-app-upnp` (`miniupnpd-nftables`), `luci-app-ddns`, `luci-app-wol` (`etherwake`), `luci-app-watchcat`, `luci-app-wifischedule`, `luci-app-usteer` (контроллер роуминга 802.11k/v/r), `luci-app-uhttpd`.
* **Мониторинг и диагностика:** `luci-app-nlbwmon` (учёт трафика по клиентам), `luci-app-statistics` (графики `collectd`: загрузка и частота CPU, RAM, `br-lan`/`wan`, Wi-Fi, conntrack, аппаратные датчики и температура MT7915E), `luci-app-ttyd` (терминал в браузере), консольные утилиты `htop`, `nano`, `curl`, `iperf3`, `ethtool`, `tcpdump-mini`, `bind-dig`, `mtr-nojson`.

## Установка

> [!IMPORTANT]
> Сначала прочитайте [страницу Xiaomi AX3200 / Redmi AX6S в вики OpenWrt](https://openwrt.org/toh/xiaomi/ax3200). Там описаны **резервное копирование разделов флеш-памяти**, **восстановление по TFTP и через UART** и проблемы отдельных ревизий железа, которые здесь не повторяются. Прошивка сторонней микропрограммы — на ваш страх и риск.

**Известные риски (по данным вики):**
* У части новых экземпляров разделы MTD сдвинуты на `-0x20000`, и sysupgrade может их «окирпичить»; на некоторых не срабатывает даже factory-образ. Сообщается, что затронуты AX3200, выпущенные **после 12/2023** с отключённым telnet. Перед первым sysupgrade роутера, установленного из `factory.bin`, выполните проверки из вики («Known Issue #1»): вывод `hexdump /dev/mtd8 | head` должен начинаться с `0000000 0dd0 edfe`, а `fw_printenv | grep -e ^flag_try -e ^boot_fw` должен показывать `boot_fw1=run boot_rd_img;bootm`.
* Софт-брик «6 перезагрузок → оранжевый индикатор» предотвращается `bootcount` этой сборки, как только OpenWrt загрузилась (см. [раздел 3](#3-защита-nvram-от-софт-брика-6-перезагрузок--оранжевый-индикатор)).

### А. Со стоковой прошивки через XMiR-Patcher (рекомендуется)
[XMiR-Patcher](https://github.com/openwrt-xiaomi/xmir-patcher) получает доступ по SSH через уязвимость стокового веб-интерфейса и сам прошивает образ. Работает в Windows, Linux и macOS.

1. Завершите первоначальную настройку стоковой прошивки (понадобится пароль веб-интерфейса) и подключите компьютер к **LAN**-порту роутера. Стоковая прошивка доступна по адресу `192.168.31.1`.
2. Скачайте XMiR-Patcher (*Code → Download ZIP*) и распакуйте.
3. Запустите: **Windows** — `run.bat`; **Linux/macOS** — установите Python 3.8+ и `openssl`, затем `./run.sh`.
4. Если адрес роутера не `192.168.31.1`, выберите `1 - Set IP-address`.
5. Выберите **`2 - Connect to device (install exploit)`** и по запросу введите пароль веб-интерфейса.
6. Выберите **`4 - Create full backup`**. Дампы всех разделов флеш-памяти сохраняются в папку `backups/` XMiR-Patcher — **сохраните их в надёжном месте**: в них уникальные для вашего экземпляра калибровочные данные, они нужны для возврата на сток и восстановления после брика.
7. Скопируйте **только** `openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin` в папку `firmware/` XMiR-Patcher (других образов там быть не должно).
8. Выберите **`7 - Install firmware (from directory "firmware")`** и дождитесь перезагрузки роутера.
9. Откройте `http://192.168.1.1` (пользователь `root`, без пароля), задайте пароль root и смените пароль Wi-Fi.

Если эксплойт не срабатывает на вашей версии стоковой прошивки, альтернативы (стоковая прошивка с telnet, методы `netmode 4`, UART) описаны в вики.

### Б. Обновление с OpenWrt 24.10 / 25.12
LuCI → *Система → Восстановление / Обновление → Установить новый образ прошивки* с файлом `...-squashfs-sysupgrade.itb` или по SSH:
```sh
sysupgrade /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb
```

### В. Обновление с OpenWrt 23.05 и старше (старая разметка)
В 24.10 изменилась разметка флеш-памяти (`ubi-loader` + UBI), поэтому sysupgrade с 23.05 невозможен. Установите `factory.bin` через `mtd`, как описано в вики («24.10 UBI layout», метод 1). Настройки сбрасываются — сначала сделайте резервную копию. После восстановления копии с 23.05 выполните:
```sh
uci set system.@system[0].compat_version="2.0"
uci commit system
```

### Г. Старые сборки, не принимающие образ `.itb`
Некоторые старые сторонние сборки 24.10 отклоняют FIT-образ с ошибкой `Cannot find ubinized rootfs in the factory FIT-image`. Вместо него прошейте «сырой» UBI-образ (его создаёт `build.sh`; вручную: `dd if=openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-factory.bin of=sysupgrade.ubi bs=512K skip=1`). Скопируйте его в `/tmp/` на роутере и выполните (настройки не сохраняются):
```sh
sysupgrade -n /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-sysupgrade.ubi
```

### Д. Обновление `ubi-loader` (при необходимости)
`sysupgrade` не трогает раздел `ubi-loader`. Чтобы обновить его до версии из этой сборки:
```sh
mtd write /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-ubi-loader.itb ubi-loader
reboot
```

### Резервное копирование и восстановление
Резервное копирование разделов, восстановление по TFTP и доступ через UART описаны на [странице вики OpenWrt](https://openwrt.org/toh/xiaomi/ax3200).

## Сборка

В корне репозитория лежат seed-конфигурация [`ax3200.config`](ax3200.config) (сгенерирована `./scripts/diffconfig.sh`) и оверлей корневой ФС [`files/`](files/).

### Автоматическая сборка через `build.sh`
[`build.sh`](build.sh) устанавливает зависимости для сборки (опционально, через `apt`), обновляет фиды, применяет `ax3200.config`, синхронизирует `vermagic` ядра (при ошибке сборка останавливается), компилирует прошивку, извлекает `sysupgrade.ubi` (с проверкой разметки `factory.bin`) и формирует `sha256sums`.

Из-за `CONFIG_ALL_KMODS=y` (см. [раздел 7](#7-совместимость-с-официальным-репозиторием-vermagic--apk)) собираются все ~1100 пакетов модулей ядра: первая сборка идёт заметно дольше, а `bin/` вырастает примерно до 140 МБ; в прошивку при этом попадают только выбранные модули. `kmod-rtl8812au-ct` исключён, так как не собирается с GCC 15 (у AX6S нет USB-порта).

На чистой Ubuntu 24.04 / 26.04 LTS или Debian:
```bash
git clone -b xq-25.12 https://github.com/Dreyk007/openwrt.git
cd openwrt
./build.sh --install-deps
```
Последующие сборки:
```bash
./build.sh        # все потоки CPU
./build.sh -j4    # своё число параллельных задач
```

### Ручная сборка
```bash
# 1. Обновление и установка фидов
./scripts/feeds update -a
./scripts/feeds install -a

# 2. Загрузка seed-конфигурации AX3200 и раскрытие всех зависимостей
cp ax3200.config .config
make defconfig

# 3. Загрузка официального vermagic ядра (обязательно после перехода на новый релиз 25.12.x)
./vermagic_update.sh mediatek mt7622

# 4. Загрузка исходников и компиляция
make download -j$(nproc)
make -j$(nproc)
```

> **Примечание:** в отличие от ядра Linux, `make defconfig` в OpenWrt **не** сбрасывает `.config` к умолчаниям — он дополняет скопированную в `.config` короткую seed-конфигурацию всеми зависимыми параметрами.

### Изменение конфигурации
Меняйте конфигурацию через `make menuconfig` и сохраняйте результат обратно как seed — не редактируйте `ax3200.config` вручную. Оставляйте `CONFIG_ALL_KMODS=y` и `# CONFIG_KERNEL_KALLSYMS is not set`: они нужны для совместимости с официальными kmods.
```bash
cp ax3200.config .config && make defconfig
make menuconfig
./scripts/diffconfig.sh > ax3200.config
```

### Обновление до нового релиза OpenWrt
В [UPGRADING.md](UPGRADING.md) (на английском) подробно описано, как влить в эту ветку новый минорный релиз (например, 25.12.7) и как перенести сборку на новый мажорный релиз: обновление vermagic, сверка конфигурации ядра с официальным SDK и проверка на устройстве.

## О проекте OpenWrt

OpenWrt — операционная система на базе Linux для встраиваемых устройств. Вместо одной статичной прошивки OpenWrt предоставляет полностью записываемую файловую систему с менеджером пакетов. Это освобождает от набора приложений и настроек производителя и позволяет настроить устройство под любую задачу с помощью пакетов. Для разработчиков OpenWrt — это платформа для создания приложений без необходимости собирать вокруг них целую прошивку; для пользователей — возможность полной настройки и применения устройства так, как производитель и не предполагал.
