# Upgrading to a New OpenWrt Release

This document describes how to move the `xq-25.12` branch of this repository to a new OpenWrt release:

* [Minor release](#2-minor-release-eg-25126--25127) — a new point release of the same series (e.g. 25.12.6 → 25.12.7). Done by **merging** the new upstream tag.
* [Major release](#3-major-release-eg-2512--26xx) — a new release series (e.g. 25.12 → 26.xx). Done by creating a **new branch** from the new upstream tag and **porting** (cherry-picking) the fork's commits.

The procedures were validated on 2026-10-20 with `git merge-tree` simulations against the real upstream history (see [Appendix A](#appendix-a-simulating-a-merge-without-touching-the-working-tree)).

## 0. Prerequisites

```bash
# Remotes: origin = this fork, upstream = official OpenWrt
git remote -v
git remote add upstream https://github.com/openwrt/openwrt.git   # only if it is missing

# Start from a clean working tree
git status

# git >= 2.38 is needed for "git merge-tree --write-tree" (Appendix A)
git --version
```

Release tags of this build follow the scheme `v<openwrt-version>-ax3200-r<N>`, e.g. `v25.12.6-ax3200-r1`.

## 2. Minor Release (e.g. 25.12.6 → 25.12.7)

Expected effort: **no conflicts**. A simulation that replayed the whole 25.12 cycle (v25.12.0 → v25.12.6, 598 upstream commits, 1367 files) against this branch produced **0 conflicts**; the 15 files changed on both sides were merged automatically.

Below, `NEW=25.12.7` and `OLD=25.12.6`.

### 2.1. Preview the merge (does not change anything)

```bash
git fetch upstream --tags
git merge-tree --write-tree --name-only HEAD v$NEW
echo $?        # 0 = clean merge; 1 = conflicts, the conflicted files are listed after the first line
```

### 2.2. Merge the new tag

The branch is published, so merge instead of rebasing:

```bash
git switch xq-25.12
git tag backup/pre-v$NEW                                   # local safety point
git merge --no-ff v$NEW -m "Merge tag 'v$NEW' into xq-25.12"
```

If a conflict happens anyway:

* `README.md` — keep ours (`git checkout --ours README.md`); upstream only has the generic OpenWrt README.
* Makefiles / scripts — keep both changes: take upstream's version and re-apply the fork's lines (see [1.2](#12-this-builds-commits)).
* `package/kernel/mt76/Makefile` — take upstream's version and set `PKG_RELEASE` one higher than upstream's, so the packages with our `03xx` patches differ from the official ones.
* `git add <file>` for each resolved file, then `git commit`.

If the new release changed `package/kernel/mt76` (a new Git HEAD or more fixes cherry-picked from Linux stable), drop the `package/kernel/mt76/patches/03xx-*.patch` that it now contains: compare their `Subject:` lines with the new upstream patches and, after a Git HEAD update, check with `git -C <mt76 clone> merge-base --is-ancestor <commit> <new PKG_SOURCE_VERSION>` (each `03xx` patch names its upstream commit). Then run `make package/kernel/mt76/{clean,compile} V=s` and make sure every remaining `03xx` patch still applies.

Check the version: `grep -nF '$(VERSION_NUMBER),$(VERSION_NUMBER),' include/version.mk` must show the new version number.

### 2.3. Update the feeds

The release commit pins new feed revisions in `feeds.conf.default`:

```bash
./scripts/feeds update -a
./scripts/feeds install -a
```

`build.sh` runs the same commands and in between applies `feeds-patches/<feed>/*.patch`; when running them by hand, apply the patches too (`git -C feeds/luci apply "$PWD"/feeds-patches/luci/*.patch`). A pinned feed is not updated once cloned, so `build.sh` first restores the files the patches touch. If a patch no longer applies to a new feed revision, the feed probably has the fix already: look for its `Subject:` in the feed's `git log` and delete the patch.

### 2.4. Update the official vermagic

Every release has a new kernel vermagic. The official kmods of the new release must already be published on `downloads.openwrt.org` (the script falls back to the official mirrors in `VERMAGIC_MIRRORS` when it does not answer), otherwise the script fails (on purpose) and keeps the old list:

```bash
./vermagic_update.sh mediatek mt7622     # creates vermagic-mediatek-mt7622-$NEW.list, removes the old list
cat vermagic-mediatek-mt7622-$NEW.list   # e.g. 6.12.xxx-1-<32 hex digits>
git add -A vermagic-mediatek-mt7622-*.list
```

If the kernel version of the release changed, the script also checks that the official repository has kmods for exactly this kernel.

### 2.5. Re-validate the seed configuration

```bash
cp ax3200.config .config && make defconfig
./scripts/diffconfig.sh > /tmp/ax3200.config.new
diff ax3200.config /tmp/ax3200.config.new
```

No output means nothing changed. Otherwise review the difference (renamed/removed packages or options), then `cp /tmp/ax3200.config.new ax3200.config`. Never edit the seed by hand.

### 2.6. Build

```bash
./build.sh
```

The build stops if there is no vermagic list for the release: when neither `downloads.openwrt.org` nor its mirrors answer, `build.sh` warns and uses the committed list of the release, since a released version keeps its vermagic. With `CONFIG_ALL_KMODS=y` all ~1100 kmods are built, so the first build after a release update takes longer. If an optional (`=m`) kmod fails to build, exclude it in the seed (as done for `kmod-rtl8812au-ct`) instead of ignoring the error. If a kernel patch no longer applies after a kernel version bump (e.g. `970-...mtk_ppe-fix-flow-accounting...` or `971-netfilter-flowtable-...`), refresh it with `make target/linux/refresh` and review the result. If OpenWrt itself backports the `mt7530` `.get_stats64` commits, the `799-0*` patches no longer apply: drop ours.

### 2.7. Check kernel configuration parity with the official build

Official kmods only work if our kernel configuration matches the official one (see README, section 7). Compare it with the `.config` from the official SDK of the new release — see [Appendix B](#appendix-b-kernel-configuration-parity-check). Only these differences are acceptable:

* compiler: `CONFIG_GCC_VERSION`, `CONFIG_CC_VERSION_TEXT`, `CONFIG_CC_HAS_*`, `CONFIG_LD_ORPHAN_WARN_LEVEL`, `CONFIG_WERROR`;
* `CONFIG_CPU_FREQ_DEFAULT_GOV_SCHEDUTIL` / `..._ONDEMAND`;
* `CONFIG_ZRAM_BACKEND_*`, `CONFIG_ZRAM_DEF_COMP*`.

Anything else (especially networking options) must be fixed before flashing the image.

### 2.8. Flash and verify on the device

```bash
# on the router
sysupgrade -T /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb   # dry run
sysupgrade    /tmp/openwrt-mediatek-mt7622-xiaomi_redmi-router-ax6s-squashfs-sysupgrade.itb
```

Then run the checks from [Appendix C](#appendix-c-on-device-verification), in particular the **official kmod load test**.

### 2.9. Update the documentation and publish

```bash
grep -rn "$OLD" README.md README.ru.md BUILDING.md BUILDING.ru.md UPGRADING.md   # version numbers, vermagic hash (README section 7)
# edit, then:
git add -A && git commit -m "Update to OpenWrt $NEW"
git push origin xq-25.12
git tag -d backup/pre-v$NEW
```

Then run *Actions → Build AX3200 firmware → Run workflow* on `xq-25.12` with an empty release tag: it builds the firmware and publishes the release `v$NEW-ax3200-r1` (see README, *Build and Release with GitHub Actions*).

## 3. Major Release (e.g. 25.12 → 26.xx)

### 3.1. Do not merge the new series into `xq-25.12`

A simulation of merging upstream `main` into `xq-25.12` produced **1093 conflicted files**, of which only **10** are files touched by this fork. The rest are conflicts between the 25.12 stable branch (backports, version bumps) and `main` — upstream never merges these branches either. Instead, a new branch is created from the new release tag and the fork's commits are ported on top of it.

### 3.2. Choose the base

* If the `remittor` tree publishes a branch for the new series, base on it: its patches are then already ported and only this build's commits have to be cherry-picked (skip [3.4](#34-port-the-remittor-patches)).
* Otherwise base on the upstream release tag:

```bash
git fetch upstream --tags
git switch -c xq-26.xx v26.xx.0
```

### 3.3. Collect the commits to port

```bash
OLDBASE=v25.12.6
git log --reverse --no-merges --format='%h %an | %s' $OLDBASE..xq-25.12
```

### 3.4. Port the remittor patches

Cherry-pick the **required** and **recommended** patches from [1.1](#11-patches-from-the-remittor-tree), oldest first. Skip the patches for other devices: they are the biggest source of conflicts and are not used by the AX3200 build.

```bash
git log v26.xx.0 --oneline --grep "improve transitive dependencies" --grep "provides/depends fix"  # already upstream?
git cherry-pick -x <commit>
```

### 3.5. Port this build's commits

```bash
git cherry-pick -x $(git log --reverse --no-merges --author=Dreyk --format=%h $OLDBASE..xq-25.12)
```

Known conflict points and how to resolve them:

| File | Resolution |
|---|---|
| `target/linux/mediatek/mt7622/config-6.12` | The kernel version of a new series usually changes, and the file becomes `config-<new kernel>`; git reports *modify/delete*. Re-apply the change to the new file: `CONFIG_CPU_FREQ_DEFAULT_GOV_SCHEDUTIL=y` and `# CONFIG_CPU_FREQ_DEFAULT_GOV_ONDEMAND is not set` (the other `DEFAULT_GOV_*` options stay unset), then `git rm` the old file. |
| `.../mt7622/base-files/etc/init.d/bootcount` | Re-add the `xiaomi,redmi-router-ax6s)` case; check that upstream did not add its own handling for this board. |
| `package/base-files/Makefile` | Re-add the `CONFIG_PACKAGE_MAC80211_*` symbols to `PKG_CONFIG_DEPENDS` (needs the remittor Wi-Fi defaults patch). |
| `package/base-files/files/bin/config_generate` | Re-apply `enable_server='1'` in the `system.ntp` block. |
| `.gitignore` | Remove the `/files` line again. |
| `README.md` | Keep ours. |
| `vermagic-mediatek-mt7622-25.12.6.list` | Delete; it is regenerated in [3.7](#37-build-flash-verify-and-publish). |

During a cherry-pick: resolve, `git add <files>`, `git cherry-pick --continue`; `git cherry-pick --skip` drops a commit that is no longer needed.

### 3.6. Re-validate every assumption of this build

A new series can change any of the underlying facts. Check each item before building:

1. **Toolchain:** the default GCC version of the new series. If it already is the version selected in the seed, drop `CONFIG_TOOLCHAINOPTS` / `CONFIG_GCC_USE_VERSION_*` from the seed.
2. **Seed configuration:** run [2.5](#25-re-validate-the-seed-configuration); review renamed/removed packages and `KERNEL_*` options.
3. **Kernel config parity:** keep `CONFIG_ALL_KMODS=y` and `# CONFIG_KERNEL_KALLSYMS is not set` and re-run [Appendix B](#appendix-b-kernel-configuration-parity-check) against the new SDK. Re-check excluded kmods (`kmod-rtl8812au-ct` may build again; other kmods may fail).
4. **Vermagic infrastructure:** `include/kernel-defaults.mk` still calls `scripts/getvermagic.sh`, and `include/feeds.mk` still adds the kmods repository line for both apk and opkg variants.
5. **Flash layout:** `DEVICE_COMPAT_VERSION` of `xiaomi_redmi-router-ax6s` in `target/linux/mediatek/image/mt7622.mk`. If it changed, sysupgrade with kept settings is refused and the README installation section needs an update.
6. **Wi-Fi / WED / HFO:** the `wed_enable` parameter of `mt7915e`, `kmod-nft-offload`, the `flow_offloading*` firewall options.
7. **Packet steering:** `package/network/config/netifd/files/usr/libexec/network/packet-steering.uc` still pins threaded NAPI and only sets the per-queue `rps_flow_cnt` (then `rps_sock_flow_entries` in `99-bbr.conf` is still needed); the decision against `irqbalance` still holds.
8. **Defaults script:** option names used by `99-custom-settings` (`https-dns-proxy` `force_dns`, `luci_statistics` plugin sections, `system.@system[0].zram_*`, procd `system.@service[0].respawn_*`, `dropbear` `Interface`), and the LuCI theme logic (`99-custom-settings`, `files/etc/init.d/luci-themes`): themes are detected by `/usr/share/ucode/luci/template/themes/<name>/header.ut` (the check LuCI itself does in `luci-base/ucode/runtime.uc`), each theme package must still register itself in `30_luci-theme-<name>` as `/luci-static/<name>` without changing an existing active theme, and `luci-theme-footstrap` must still be available.
9. **Sysctl names** in `99-bbr.conf` (`sysctl -a` on the device after flashing).
10. **NVRAM anti-brick:** the U-Boot variables used by `bootcount` are still the right ones.
11. **PPE accounting patch (`970-...`):** check whether `generic/pending-*/736-04-net-ethernet-mediatek-fix-ppe-flow-accounting-for-L2.patch` still exists and whether upstream reworked the PPE accounting. Refresh the patch, or drop it if the bug is fixed; verify with a large download through the router that `nlbw -c show` grows by the downloaded amount and never jumps by ~4 GB, and with the bucket test of [RESEARCH.md section 3](RESEARCH.md#3-traffic-accounting-with-hardware-offloading) that a flow keeps counting when another flow binds in its PPE bucket.
12. **Flowtable teardown patch (`971-...`):** check whether upstream `flow_offload_work_del()` in `net/netfilter/nf_flow_table_offload.c` now fetches the flow stats itself; drop the patch then, otherwise refresh it. It works together with the MIB read in `970-...`: after a TCP FIN the PPE unbinds the entry by itself, so the final poll has to read the hardware counter of an unbound entry. Verify with downloads that close their connection right after the transfer (e.g. `curl -o /dev/null` of a 300 MiB file, and 30 x 10 MiB on separate connections): after ~40 s (`nlbwmon` refresh interval) `nlbw -c show` must have grown by the downloaded amount plus ~5% headers, not by 50-85% (300 MiB) or ~4% (10 MiB) of it.
13. **`mt7530` port counters backport (`generic/backport-6.12/799-0*`):** kernels from 6.16 on have `.get_stats64`, so drop `799-01`…`799-06`. Keep `799-07` (or drop it too) depending on whether the new kernel already has `07d995873960` ("net: dsa: mt7530: fix .get_stats64 sleeping in atomic context", Linux 7.1, likely backported to 6.18.y stable): without it reading `/proc/net/dev` logs "BUG: sleeping function called from invalid context". Verify that `cat /sys/class/net/wan/statistics/rx_bytes` grows by the downloaded amount during an offloaded download and that `dmesg` stays clean.
14. **mt76 fixes (`package/kernel/mt76/patches/03xx-*.patch`):** a new series builds a newer mt76, so most of them are included already; drop those as described in [2.2](#22-merge-the-new-tag). After flashing, check `cat /sys/kernel/debug/ieee80211/wl0/mt76/radio` a few times: on a busy 2.4 GHz channel the sensitivity must move away from `ofdm=-98 cck=-110` (SCS working).
15. **Feed patches (`feeds-patches/<feed>/*.patch`):** the new series pins newer feeds; drop the patches they contain (`build.sh` stops at a patch that does not apply, see [2.3](#23-update-the-feeds)).
16. **SmartRG flowtable patches (`972`–`975`):** check whether upstream or OpenWrt took them or an equivalent (compare with the current `990-08-*` patches of the SmartRG tree) and drop or refresh them; `975` must follow `971`. Verify with the firewall reload test of [RESEARCH.md section 3](RESEARCH.md#3-traffic-accounting-with-hardware-offloading): an offloaded flow keeps counting across `/etc/init.d/firewall reload` and leaves no entry in `/sys/kernel/debug/ppe0/bind`.
17. **Wi-Fi flowtable hotplug (`20-firewall-wifi`):** check whether the new kernel adds a returning device to a flowtable by itself (`nf_tables_flowtable_event()` in `net/netfilter/nf_tables_api.c` handling `NETDEV_REGISTER`); drop the script then. Verify: after `wifi down; wifi up`, `nft list flowtable inet fw4 ft` lists the `wl*-ap0` devices again within ~10 s.

18. **bridger and `976-...`:** bridger stays in the image but off by default (enabled only by the *Maximum throughput* operating mode) (it costs latency and fairness with several busy Wi-Fi clients, [RESEARCH.md section 12](RESEARCH.md#12-several-wi-fi-clients-latency-and-wed)); re-run those tests if a new mt76 or WED version changes the hardware path. Keep the bridger update only while the series' bridger is older than `2a2d126` (2026-09-17). Check whether `generic/pending-*/736-03-…` still clears `entry` instead of `cur` after `mtk_flow_entry_update(ppe, cur, …)` fails in `mtk_flow_entry_update_l2()`; drop `976` once it is fixed. Keep `patches/100-…` while upstream `__device_update()` in `device.c` still attaches the port before it sets `dev->offload_dev`. Verify with [RESEARCH.md section 11](RESEARCH.md#11-wi-fi--lan-throughput-and-bridger): two transfers from a wired PC to a 5 GHz client one after the other, the second one must also run at ~10 % router CPU, and the `Sent hardware` counter in `tc -s filter show dev eth0 ingress` must grow during both; after `kill -9 $(pidof bridger)` during a transfer the restarted bridger must replace the rule (its counter starts from 0).
19. **BPF toolchain:** the seed sets `CONFIG_BPF_TOOLCHAIN_HOST=y`, so the BPF program of `bridger` is compiled with the build host's `clang`/`llvm` (installed by `build.sh --install-deps`) instead of OpenWrt's `tools/llvm-bpf`. The flags come from `include/bpf.mk` either way (`-mcpu=v3`) and the kernel verifier checks the program when `bridger` loads it, so a bad compiler shows up at once as a `bridger` that does not start. OpenWrt 25.12 builds LLVM 21.1.6, the same version as Ubuntu 26.04 (the default runner); Ubuntu 24.04 has LLVM 18, which also works but gives a BPF object that is not byte-identical. Building LLVM from source (`CONFIG_BPF_TOOLCHAIN_BUILD_LLVM=y`) gives the same compiler on every host, but adds a long host-tool build (tens of minutes on the 24-thread build PC, hours on a 4-core runner) and several GB of disk. For a new series, check that the host `clang` is at least `CLANG_MIN_VER` in `include/bpf.mk` and that `bpf.mk` still finds `llc`, `opt`, `llvm-dis` and `llvm-strip` without a version suffix (Ubuntu's `llvm` package provides them).
20. **Operating modes (`luci-app-tuning`):** the page and the `tuning` command write `firewall` `flow_offloading`/`flow_offloading_hw`, `network.globals.packet_steering`, `cpufreq.settings.governor`, the first `sqm` `queue` (`enabled`, `interface`, `download`, `upload`, `qdisc`, `script`), `options mt7915e wed_enable` in `/etc/modules.conf`, and enable or disable `/etc/init.d/bridger`. Check these names and the init scripts (`firewall`, `packet_steering`, `sqm`) in the new series, and that the modes of `tuning.uc` still match the measurements (re-run the tests of RESEARCH.md sections 9, 11–13 when the hardware path, mac80211 or the packet steering script change). After flashing: `tuning set lowlatency`, `reboot`, `tuning status` shows `lowlatency` with `wed_running` false; `tuning set balanced`, `reboot`.
21. **Firmware updates (`luci-app-fwupdate`):** the update check relies on `uclient-fetch` following GitHub's redirects, `ubus call system validate_firmware_image` and `sysupgrade -T`/`-n` behaving as in 25.12. For a new series check them, and keep the tag format `v<OpenWrt version>-ax3200-r<N>`, which the router compares. If a release cannot be installed over the previous one with kept settings (new flash layout, `DEVICE_COMPAT_VERSION`, incompatible settings), run the workflow with `upgrade: manual` or `reset` and the notes.

### 3.7. Build, flash, verify and publish

1. Generate the vermagic list: `./vermagic_update.sh mediatek mt7622` (needs published official kmods of the new release), commit it.
2. Build with `./build.sh`, check kernel parity ([Appendix B](#appendix-b-kernel-configuration-parity-check)).
3. Flash. When moving between series, start with `sysupgrade -T` and read the compatibility message; a clean flash (`sysupgrade -n`) is the safe default for a major upgrade. Keep a configuration backup (`sysupgrade -b`).
4. Run the full [Appendix C](#appendix-c-on-device-verification) checklist.
5. Update the README and BUILDING files (versions, the branch name in `git clone -b xq-25.12 …` in BUILDING, vermagic hash, any changed facts) and this document.
6. Publish the new branch and a release tag:

```bash
git push -u origin xq-26.xx
```

   Make `xq-26.xx` the default branch on GitHub (*Settings → General → Default branch*), so that the workflow and the README links point to it, then run *Actions → Build AX3200 firmware → Run workflow* on `xq-26.xx`; it publishes the release `v26.xx.0-ax3200-r1`. Check that the OpenWrt CI workflows that came with the new release branch are disabled.

## Appendix A: Simulating a Merge Without Touching the Working Tree

`git merge-tree` performs a merge in memory and lists the conflicted files; the branch and the working tree are not modified.

```bash
# Real merge of an upstream ref into the current branch
git merge-tree --write-tree --name-only HEAD v25.12.7

# Proxy for a future update of a similar size: replay an older upstream range in reverse.
# Conflicts appear exactly where those upstream changes overlap with the fork's changes.
git merge-tree --write-tree --name-only --merge-base=v25.12.6 HEAD v25.12.5   # size of one point release
git merge-tree --write-tree --name-only --merge-base=v25.12.6 HEAD v25.12.0   # whole series so far
```

The first output line is a tree ID; with exit code 1 the following lines are the conflicted files.

## Appendix B: Kernel Configuration Parity Check

1. Get the kernel `.config` of the official build from the SDK of the release (the archive is ~250 MB; only one file is extracted):

```bash
VER=25.12.7
URL=https://downloads.openwrt.org/releases/$VER/targets/mediatek/mt7622
SDK=$(curl -fsS $URL/ | grep -oE 'openwrt-sdk-[^"]+\.tar\.zst' | head -1)
mkdir -p /tmp/sdk && curl -fsS "$URL/$SDK" | tar --zstd -x -C /tmp/sdk --wildcards '*/linux-mediatek_mt7622/linux-*/.config'
OFFICIAL=$(find /tmp/sdk -path '*linux-mediatek_mt7622/linux-*/.config' | head -1)
OURS=$(ls -d build_dir/target-aarch64_cortex-a53_musl/linux-mediatek_mt7622/linux-*/.config | head -1)
```

2. Compare them (symbols missing from a file count as `n`):

```bash
python3 - "$OFFICIAL" "$OURS" <<'EOF'
import re, sys
def load(path):
    d = {}
    for line in open(path):
        m = re.match(r"# (CONFIG_\S+) is not set", line)
        if m:
            d[m.group(1)] = "n"
        elif line.startswith("CONFIG_"):
            k, _, v = line.rstrip("\n").partition("=")
            d[k] = v
    return d
a, b = load(sys.argv[1]), load(sys.argv[2])
diff = [(k, a.get(k, "n"), b.get(k, "n")) for k in sorted(set(a) | set(b)) if a.get(k, "n") != b.get(k, "n")]
print(f"{len(diff)} differences")
for k, x, y in diff:
    print(f"  {k}: official={x} ours={y}")
EOF
```

For 25.12.6 the result was 14 differences, all from the acceptable list in [2.7](#27-check-kernel-configuration-parity-with-the-official-build).

3. Optional: compare the `struct module` size of an official and of our module (it must be equal, 640 bytes on 25.12.6):

```bash
readelf -SW <module>.ko | grep gnu.linkonce.this_module
```

## Appendix C: On-Device Verification

```bash
# Version and kernel
grep DISTRIB_DESCRIPTION /etc/openwrt_release; cat /proc/version
ls /proc/kallsyms 2>/dev/null || echo "KALLSYMS disabled (expected)"
ls /etc/uci-defaults/          # must be empty: all first-boot scripts succeeded

# Official kmod load test
apk update
apk add kmod-dummy && modprobe dummy && ip link add test0 type dummy && ip link del test0 && echo "official kmod OK"
dmesg | grep -i "section size must match"   # must print nothing
rmmod dummy; apk del kmod-dummy

# Optimizations
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_governor               # schedutil
cat /sys/module/mt7915e/parameters/wed_enable                              # Y
nft list flowtables | grep "flags offload"                                 # hardware offload
cat /proc/sys/net/core/rps_sock_flow_entries                               # 1024
sysctl net.ipv4.tcp_congestion_control net.netfilter.nf_conntrack_max      # bbr, 32768
cat /proc/swaps; cat /sys/block/zram0/comp_algorithm                       # zram0, [lz4]
for i in $(grep ethernet /proc/interrupts | cut -d: -f1); do cat /proc/irq/$i/effective_affinity_list; done
for p in $(pgrep -f napi/); do echo "$(cat /proc/$p/comm) $(grep Cpus_allowed_list /proc/$p/status | cut -f2)"; done
logread | grep bootcount                                                   # "nvram verified"
tuning status | grep '"profile"'                                          # "balanced"
pidof bridger || echo "bridger off"                                         # bridger off (default)

# Services
nslookup openwrt.org 127.0.0.1                 # DNS through https-dns-proxy
uci get https-dns-proxy.config.force_dns       # 0
iwinfo | grep -E "ESSID|Channel|Encryption"
logread | grep -iE "error|fail" | tail -20
```

While traffic flows through the router, `grep -c BND /sys/kernel/debug/ppe0/bind` (PPE entries) and `[HW_OFFLOAD]` entries in `/proc/net/nf_conntrack` confirm that hardware flow offloading is active. While a wired PC sends to a 5 GHz client, `tc -s filter show dev eth0 ingress` lists its `bridger` rule with `in_hw` and a growing `Sent hardware` counter.
